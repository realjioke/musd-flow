# MUSD Flow — Security Notes

Status: reviewed 2026-10-25, pre-audit. This is a design review, **not** an
independent audit, and we do not claim one.

## Authentication & authorization

- **Wallet challenge auth** for all state-changing writes that create resources
  (payment requests, circles, joining circles): single-use nonce (10-min TTL) bound
  to `(address, action)` and SHA-256 payload hash; server recovers the signer with
  `verifyMessage` and burns the nonce. Nobody can create/join/spend anything on your
  behalf without your wallet signature.
- **Contribution claiming needs no signature** by design: a contribution is only
  counted when the *on-chain Transfer event* matches `from == declared member` and
  `to == circle payout address`. Attributing it differently is impossible regardless
  of who clicks.
- Circle **payout address is creator-chosen** and displayed in the app/UI; MUSD Flow
  never custody funds, never signs a transfer for a group, and has no withdrawal
  function to attack.

## Input validation

- Every API body is parsed server-side with a strict Zod schema: chain IDs limited to
  verified MUSD chains, addresses/hashes regex-checked, amounts regex-checked decimal
  strings (≤18 fraction digits), memo lengths capped.
- Public IDs are generated by `nanoid` with an alphabet that cannot traverse paths,
  and lookups key on them directly.

## Onchain truth

- Payment requests and circle contributions are only marked after the server fetches
  the actual `eth_getTransactionReceipt` and finds a matching `Transfer` event of the
  request's token contract — correct token, chain, destination, senders and amount.
- `(circle_id, tx_hash, log_index)` unique index makes contribution recording
  idempotent; replaying the same hash never double-counts.
- Amounts are decimal strings in the DB; Wei is processed only as bigint. No floats
  touch token arithmetic anywhere.

## Abuse resistance

- D1-backed fixed-window rate limiting per IP bucket on sensitive routes:
  nonce issuance 8/min, creations 10/min, verification 20/min, reads 120/min.
  A limit-breach returns 429 with `Retry-After` semantics.
- Payment requests and circles are global objects — their content is public by
  design; we deliberately minimize what is stored (amount, memo ≤280 chars, addresses).
  No PII beyond what the user types.

## Current limitations (disclosed, not hidden)

1. Rate limiting depends on `x-forwarded-for`/`cf-connecting-ip`; behind an
   untrusted proxy these can be spoofed. On Cloudflare, `cf-connecting-ip` is
   trustworthy, so deployed preview/prod limits are sound; local dev limits are only
   advisory.
2. Only server-side Zod + browser-surface protections cover forms; a full CSP and
   header hardening pass (HSTS, frame-ancestors) is still to be added at the edge.
3. No SIWE/session model: features are wallet-signature-scoped instead, which keeps
   the DB schema PII-free but means list views are per-address-claimed (an address
   string in a URL). Acceptable for v1 since rows are public anyway.
4. Bridges are *not* executed in-app (appoval/cross-chain risk consciously avoided);
   Smart Route links to the official Portal UI instead.
5. Dependencies were installed clean (0 vulnerabilities at install time); a
   scheduled `npm audit` in CI is on the roadmap.
